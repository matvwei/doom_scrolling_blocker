# Спецификация: Doomscroll Blocker

Браузерное расширение (Manifest V3, Chrome и Edge) против doomscrolling.
Без backend, без отправки данных наружу: всё хранится в `chrome.storage.local`.

## 1. Отслеживаемые цели

Цель — встроенный сервис или пользовательский сайт. Классификация выполняется
в `core/matching.ts` по URL вкладки, поэтому SPA-навигация (переходы без
перезагрузки страницы) обрабатывается корректно: background слушает
`chrome.tabs.onUpdated`, а content script периодически пересылает своё состояние.

### 1.1. Встроенные сервисы

| Сервис | Зоны отслеживания | Что НЕ затрагивается |
|---|---|---|
| YouTube | **Область «Только Shorts» (default):** `/shorts` и `/shorts/*` (включая `m.youtube.com`). **Область «Весь YouTube»:** любые страницы `www.youtube.com` и `m.youtube.com` — обычные видео `/watch`, главная `/`, `/feed/*`, поиск | при области «только Shorts»: обычный YouTube; `studio.youtube.com`, `music.youtube.com` никогда не входят в область |
| Instagram Reels | главная лента `/`, `/reels/*`, `/reel/*` | профили `/username/`, посты `/p/*`, сообщения `/direct/*`, `/explore/` |
| TikTok | весь сайт `tiktok.com` | — |

`youtubeScope` хранится в конфигурации (`'shorts' | 'all'`, default `'shorts'` —
обратная совместимость с MVP). Смена области применяется без переустановки:
background переклассифицирует все вкладки с известным URL, overlay
показывается/скрывается по факту новой классификации.

### 1.2. Пользовательские сайты (custom rules)

Пользователь добавляет собственные правила через настройки (встроенные в popup
или страницу options, UI, без JSON):
понятное имя + адрес + тот же набор настроек, что у встроенных сервисов
(`enabled/sessionLimitMinutes/dailyLimitMinutes/action/redirectUrl/message`).
У каждого сайта — **независимые счётчики** (ключ состояния — id сайта).

Синтаксис адреса (`core/customSites.ts`):

- `https://example.com` — домен и все поддомены, любые пути;
- `https://example.com/foo` — домен и поддомены, раздел `/foo` и всё ниже
  (path prefix с границей компонента: `/foobar` не совпадает);
- схема учитывается строго (правило `https` не ловит `http`);
- отклоняются некорректные/опасные URL: без схемы, не http/https, с
  `user:pass@`, с нестандартным портом (не выражается в match-паттернах Chrome),
  `javascript:`/`data:`/`chrome:` и т.п. Query и hash из правила отбрасываются.

Семантика совпадений:

- Пользовательские правила проверяются **раньше** встроенных: явно добавленное
  правило для, например, `youtube.com` действует на весь YouTube независимо от
  встроенной области (встроенный сервис при этом не ломается — он просто
  «затенён» для совпадающих URL).
- При нескольких правилах одного домена выигрывает первое в порядке списка.

## 2. Конфигурация

```ts
interface ExtensionConfig {
  version: 2;
  youtubeScope: 'shorts' | 'all';      // default: 'shorts'
  services: Record<ServiceId, ServiceConfig>;   // youtube | instagram | tiktok
  customSites: CustomSiteConfig[];
}

interface ServiceConfig {
  enabled: boolean;            // default: true
  sessionLimitMinutes: number; // default: 15, целое 0..720
  dailyLimitMinutes: number;   // default: 45, целое 0..1440
  action: 'close' | 'redirect' | 'warning'; // default: 'warning'
  redirectUrl: string;         // default: '', обязателен и валиден (http/https) только для action='redirect'
  message: string;             // default: 'Хватит doomscrollить. Пора вернуться к делам'
}

interface CustomSiteConfig extends ServiceConfig {
  id: string;    // генерируется при добавлении
  name: string;  // понятное имя для popup/options/overlay
  url: string;   // адрес правила, см. 1.2
}
```

Правила валидации (`core/config.ts`):
- лимиты — целые числа в допустимых границах; **0 допустим и означает
  «блокировать сразу»** (UI явно подписывает это рядом с полями лимитов);
- `redirectUrl` обязателен и должен быть `http://`/`https://` только при
  `action='redirect'`;
- `redirectUrl` не должен вести в отслеживаемую зону (любой URL, классифицируемый
  по текущей конфигурации: встроенные сервисы с учётом области YouTube + все
  custom-сайты) — иначе перенаправление мгновенно попадало бы под блокировку
  снова. Background дополнительно страхуется в runtime: если такой URL всё же
  оказался в конфигурации, вместо перенаправления показывается warning;
- `message` — непустая строка до 500 символов; `name` custom-сайта — непустая
  строка до 100 символов;
- повреждённые данные из хранилища нормализуются (`normalizeConfig`), см. §7.

## 3. Разрешения и регистрация content script для custom-сайтов

- Постоянный широкий доступ ко всем сайтам **не запрашивается**: в
  `host_permissions` манифеста — только встроенные сервисы. `<all_urls>` в
  обязательных правах отсутствует.
- Для custom-сайтов используются `optional_host_permissions:
  ['http://*/*', 'https://*/*']`. При сохранении настроек (клик «Сохранить»
  во встроенных настройках popup или на странице options) вызывается
  `chrome.permissions.request({ origins })` **из пользовательского действия**
  через `adapters/permissions.ts`. Запрашивается минимально
  необходимый origin — паттерн вида `https://*.example.com/*` (wildcard-хост
  покрывает домен и поддомены; путь в правах доступа не ограничивается).
- **Отказ в разрешении:** настройки не сохраняются, сайт не добавляется,
  показывается понятная ошибка — сайт не считается активным молча.
- Content script на custom-доменах регистрируется динамически
  (`chrome.scripting.registerContentScripts`, `persistAcrossSessions: true`,
  id `dsb-custom-<siteId>`) через `adapters/scripting.ts`:
  - домен — `scheme://*.domain/*`;
  - раздел — `scheme://*.domain/path` + `scheme://*.domain/path/*` (чтобы страница
    раздела без trailing slash тоже получала скрипт).
- Background при старте (SW/браузер) сверяет зарегистрированные скрипты с
  конфигурацией: лишние снимает, совпадающие сохраняет (это же восстановление
  persistAcrossSessions после перезапуска), а при **расхождении существенных
  полей регистрации** (прежде всего `matches` после редактирования адреса
  сайта, также `js`/`runAt`/`persistAcrossSessions`, если API их возвращает) —
  перерегистрирует (unregister+register), чтобы блокировка не оставалась на
  старом пути. Поля, которые API не вернул, не сравниваются — restore после
  перезапуска не даёт ложных перерегистраций. При ошибке duplicate —
  повтор без точного пути; ошибка одного правила не мешает остальным.
- **Уже открытые вкладки:** при добавлении сайта background досылает скрипт во
  вкладки, URL которых подпадает под правило (ping → при отсутствии ответа
  `chrome.scripting.executeScript`; дубликатов слушателей нет — content script
  дедуплицируется по метке в DOM). Для показа overlay на «чужих» вкладках
  действует и запасная инъекция в `overlayMessage`.
- **Удаление сайта:** регистрация снимается, состояние (usage) вычищается,
  overlay на открытых вкладках скрывается, вкладки переклассифицируются.
  После сохранения отзываются optional origins, которые больше не используются
  ни одним сайтом (встроенные права манифеста не трогаются).

## 4. Учёт времени

- Время засчитывается, только когда вкладка **активна** (`tab.active`), окно **в
  фокусе** (`window.focused`) и документ **видим и в фокусе**
  (`document.visibilityState`, `document.hasFocus()` — content script сообщает
  background через heartbeat раз в 5 с и по событиям `visibilitychange`/`focus`/`blur`).
- Дважды время не считается: за цель начисляется не более одного «тика» за
  секунду независимо от числа открытых вкладок.
- **Сессия** сбрасывается после 10 минут вне отслеживаемых страниц или
  неактивности (`SESSION_RESET_AFTER_MS`). Дневной счётчик при этом сохраняется.
- **Дневной лимит** сбрасывается в локальную полночь (ключ дня `YYYY-MM-DD`
  локального времени). Смена дня обнуляет и сессию.
- Оба лимита работают одновременно; причина блокировки — приоритетно `session`,
  затем `daily` (при обоих лимитах 0 причина — `session`).
- **Нулевые лимиты (0 — блокировать сразу).** Превышение вычисляется по текущим
  счётчикам без ожидания накопления активного времени: действие срабатывает при
  первом же входе/переходе на отслеживаемую страницу (в т.ч. новой и фоновой
  вкладки через `onUpdated`/`onActivated`), не дожидаясь минутного тика.
  Работает для встроенных и custom целей, для всех действий (warning/close/
  redirect). Отключённая цель (`enabled=false`) с нулевыми лимитами не блокирует.
- Состояние и статистика переживают перезапуск service worker и браузера:
  снапшоты сбрасываются в `chrome.storage.local` не чаще раза в 5 с, приостановку
  SW подстраховывают будильник-вачдог (30 с) и heartbeat-тики от content script.
- Отключение цели (`enabled=false`): время не засчитывается, превышение не
  вычисляется, активная блокировка снимается, счётчики сохраняются; background
  немедленно скрывает overlay со всех вкладок цели и не выполняет enforcement.
  Уменьшение лимита ниже текущего значения применяется при следующей секундной
  проверке.
- Один тик учитывает не более 60 с, чтобы после сна/перезапуска не было скачка.
  Тик выполняется и с нулевой дельтой, чтобы зафиксировать блокировку при
  нулевых лимитах без ожидания активности.

## 5. Действия при исчерпании лимита

- `close` — закрывается только текущая (активная отслеживаемая) вкладка.
- `redirect` — текущая вкладка переходит на `redirectUrl`.
- `warning` — полноэкранный блокирующий overlay (Shadow DOM): имя цели, причина
  (`session`/`daily` с лимитом), пользовательский текст, кнопка «Закрыть
  вкладку» и кнопка «Перейти», только если `redirectUrl` настроен. Overlay
  нельзя закрыть для продолжения просмотра; дубликатов нет.
- **Мультитаб:** пока `blockedReason` цели активен, блокировка применяется к
  *каждой* отслеживаемой вкладке цели — при появлении вкладки, активации,
  навигации (включая SPA). Warning идемпотентен, close/redirect применяются к
  вкладке однократно, но каждая новая вкладка цели обрабатывается заново.
- **Снятие блокировки с вкладки:** при переходе цели в unblocked (рост лимита,
  сброс сессии/дня, отключение, удаление custom-сайта) overlay скрывается
  гарантированно и независимо от per-tab флагов; при SPA-уходе на
  неотслеживаемый URL или смене цели — через `reclassifyTab`.
- Повторный вход на отслеживаемую страницу после исчерпания лимита приводит к
  повторной блокировке (защёлка снимается, когда не осталось открытых страниц
  цели).

## 6. UI

- **Popup** имеет два view в одном окне: **dashboard** и **настройки**.
  - Dashboard: встроенные сервисы (подпись YouTube зависит от области) и
    custom-сайты: переключатель `enabled`, оставшееся session/daily время,
    бейдж «Лимит исчерпан». Список прокручивается при большом числе сайтов.
    Обновляется по событию `storage.onChanged` и раз в секунду.
  - Настройки: кнопка «Настройки» переключает view dashboard ↔ settings внутри
    самого popup (без `chrome.runtime.openOptionsPage` и без новой вкладки),
    кнопка «← Назад» возвращает на dashboard. Это тот же общий компонент
    настроек, что и на странице options — полная настройка built-ins и custom
    сайтов доступна из popup. Страница `options.html` сохранена как fallback
    (chrome://extensions → «Параметры»).
  - Popup имеет фиксированную ширину (~360px) и `max-height` с вертикальной
    прокруткой только при необходимости; горизонтального переполнения нет
    (длинные имена/URL/ошибки переносятся).
- **Настройки** (общий компонент `components/SettingsApp.tsx`, два режима:
  полная страница и компактный в popup): карточки встроенных сервисов (у
  YouTube — переключатель области) и раздел «Пользовательские сайты». Форма
  добавления нового сайта — строго одна колонка: название, адрес, включён,
  лимиты сессии/дня, действие, URL перенаправления (при выборе redirect),
  сообщение, кнопка «Добавить сайт»; добавленный сайт попадает в список
  карточек с тем же набором полей (проверка формата и дубликатов адреса).
  Карточки сайтов редактируются независимо (при смене адреса на сохранении
  перезапрашивается разрешение), удаление через `window.confirm`.
  «Сохранить» сохраняет только валидную конфигурацию и только с
  подтверждёнными разрешениями; изменения применяются background'ом сразу
  после сохранения.
- **Прерванное сохранение.** Если на сохранении нужен нативный prompt
  разрешений, конфигурация сначала записывается черновиком
  (`dsb:pendingConfig`): Chrome закрывает popup на время показа запроса.
  Background по событию `permissions.onAdded` досохраняет черновик, когда
  доступ выдан; при повторном открытии настроек черновик достраивается
  автоматически (если разрешения уже есть) либо форма восстанавливается из
  него с пояснением и кнопкой повторного сохранения. Отказ пользователя =
  настройки не сохранены, ошибка показана, введённые данные не теряются.
- **Свежесть черновика.** Любое сохранение `dsb:config` (через storage adapter
  или любую запись в хранилище — background инвалидирует черновик по
  `storage.onChanged`) отбрасывает черновик: он построен от устаревшего
  состояния и не должен перезаписывать более новый config (например, toggle
  с dashboard). Resume-ветки перечитывают черновик непосредственно перед
  записью, чтобы не перезаписать config, сохранённый между проверкой
  разрешений и записью. Повреждённый черновик никогда не применяется —
  только очищается.
- Поля лимитов в UI подписаны «0 — блокировать сразу»; `min` инпутов — 0.

## 7. Хранилище и миграции

- `dsb:config` — `ExtensionConfig` (version 2). Хранилище MVP (version 1: только
  `services`) нормализуется без потерь: `youtubeScope='shorts'` (прежнее
  поведение), `customSites=[]`; все поля сервисов сохраняются, повреждённые
  значения — к дефолтам/границам.
- `dsb:state` — `Record<targetId, ServiceState>`: встроенные сервисы и
  custom-сайты. Счётчики не привязаны к версии конфигурации и не теряются при
  миграции. Background при загрузке отбрасывает ключи состояния целей, которых
  нет в конфигурации (usage удалённых сайтов исчезает), пересчитывает смену дня
  и 10-минутный сброс сессии.
- `dsb:pendingConfig` — черновик `ExtensionConfig`, записанный до нативного
  prompt разрешений (popup закрывается на запросе доступа). Достраивается
  background'ом по `permissions.onAdded` либо при повторном открытии настроек;
  очищается после успешного сохранения/сброса. Любое сохранение `dsb:config`
  инвалидирует черновик (свежесть: stale-черновик не перезаписывает новый
  config); resume-ветки перечитывают черновик перед записью. Повреждённый
  черновик (не well-formed, не проходит валидацию) не применяется и
  гарантированно очищается.
- Custom-сайты с неразбираемым адресом при нормализации отбрасываются; поля
  чинятся; дублирующиеся id — перевыпускаются.

## 8. Архитектура

```
core/             чистый домен, без API браузера (юнит-тестируется)
  services.ts     реестр сервисов, правила путей, подписи с учётом области YouTube
  customSites.ts  синтаксис адресов custom-правил, сопоставление, match-паттерны
  matching.ts     classifyUrl(url, config) -> TargetRef | null (custom раньше builtin)
  config.ts       типы v2, defaults, валидация (0 допустим), normalizeConfig/миграции
  limits.ts       ServiceState, tickServiceState, getExceeded, rehydrate, remaining
  time.ts         localDayKey, formatClock
  messages.ts     контракты сообщений content <-> background
adapters/
  storage.ts      chrome.storage.local: конфиг и состояние, fallback к дефолтам,
                  черновик прерванного сохранения (dsb:pendingConfig), его
                  инвалидация при любом сохранении config
  pendingResume.ts безопасная проверка/достройка черновика (свежесть, очистка
                  повреждённого)
  permissions.ts  optional host permissions: запрос/сбор неиспользуемых/проверка
  scripting.ts    динамическая регистрация content script для custom-доменов,
                  reconcile после перезапуска, инъекция в уже открытые вкладки
components/
  SettingsApp.tsx общий UI настроек: полная страница options и компактный
                  view в popup (бизнес-логика не дублируется)
entrypoints/
  background.ts   service worker: вкладки/окна/фокус, тикер 1 с, действия,
                  reconcile регистраций, переклассификация при смене конфигурации,
                  досохранение черновика по permissions.onAdded
  content.ts      heartbeat видимости, overlay в Shadow DOM (единый для всех доменов)
  popup/          React UI: dashboard + встроенные настройки (view-переключение)
  options/        React UI: та же страница настроек как fallback
hooks/            useExtensionData — данные из storage для React
```

Бизнес-логика находится в `core/`, компоненты React только отображают данные и
вызывают адаптеры. Background не содержит решающей логики лимитов — только
оркестрацию.

## 9. Manifest

- permissions: `storage`, `alarms`, `scripting` (последний — динамическая
  регистрация content script для custom-доменов и запасная инъекция overlay).
- host_permissions: только `youtube.com`, `instagram.com`, `tiktok.com` (www/m).
- optional_host_permissions: `http://*/*`, `https://*/*` — выдаются точечно под
  каждый custom-сайт через `chrome.permissions.request`.
- Background — service worker, popup и options подключены штатно. Единый content
  script статически подключён только ко встроенным хостам; для custom-доменов —
  динамическая регистрация (см. §3).

## 10. Тестирование

- Юнит: `npm test` (Vitest + RTL, jsdom) — matching (встроенные/область YouTube/
  custom: домен, поддомены, path prefix, схема, приоритеты), customSites
  (парсинг/нормализация/опасные URL/паттерны), конфигурация (валидация включая
  0, normalize/миграции MVP, повреждённые custom-сайты), лимиты (включая
  нулевые: немедленное превышение, зачёлка, приоритет session), storage

  (request/отказ/duplicate/unregister/inject), React-компоненты настроек
